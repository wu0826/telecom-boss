# 洋基電信服務與商品展示網站規劃

> 規劃狀態：設計與內容發想稿（2026-08-17）  
> 範圍：先完成桌面版內容架構、每頁 HTML/PHP 分工與首頁互動契約；手機版只保留不破版的驗收條件，暫不展開手機專用版型。

## 0. 先看結論

這個網站不應該是一張把所有服務塞在一起的首頁，而應該是一個「入口首頁 + 可獨立分享的服務頁 + 可獨立分享的商品頁」系統：

1. 首頁負責讓訪客快速選擇「網路、租賃、工程、商品」四條路徑。
2. 服務頁負責解釋使用情境、解決方案、流程與適用對象。
3. 商品頁負責展示規格、套裝內容、品牌、適用場景與詢價 CTA。
4. 每個頁面都保留回首頁、麵包屑、相關服務與同一個「諮詢／估價」入口。
5. 先用獨立 `.html` 檔建立內容邊界；只有需要伺服器端資料、報價計算或權限判斷時才使用 `.php`。目前專案的 Node.js 靜態伺服器不需要為了內容頁另引入 PHP runtime。

### 不直接複製的地方

- 不把所有分類一次展開成長篇清單；桌面版使用「服務入口 + 子分類抽屜」，避免訪客迷路。
- 不讓商品頁只剩型號與規格；每個商品都要先回答「這個組合替誰解決什麼問題」。
- 不把品牌、服務、產品、工程案例混成同一種卡片；四者使用不同的資訊密度與 CTA。
- 不以輪播取代內容。輪播只用來展示 2–4 個真的需要曝光的主題，鍵盤與停留控制要完整。

## 2. Canvas 視覺哲學：Signal Atlas／訊號地圖

Signal Atlas 把網站想像成一張可以閱讀的連線地圖：服務不是堆在頁面上的卡片，而是從「需求」出發，經過網路、設備、工程與維運，抵達一個清楚的結果。空間使用像配線圖一樣的主網格，主線負責導覽，支線負責比較與細節；每個頁面只保留一條最重要的閱讀路徑，讓訪客知道下一步要往哪裡走。

色彩使用深海軍藍作為可靠的底、青綠作為正在流動的訊號、珊瑚橘作為優惠或需要注意的節點，黃色只保留給焦點與鍵盤操作。材質保持平面、清楚、接近印刷圖表，不依賴大量漸層、玻璃效果或厚重陰影。每一個色塊都必須有語意：服務狀態、速度、優惠、可操作性或路徑方向。

比例採用「一個大命題 + 一組可掃描資料 + 一個動作」的節奏。英雄區可以有一個大尺寸的網路節點或工程剖面圖，但標題不要同時塞入多個賣點；速度、價格、服務範圍、適用情境以小型資料標籤排列，讓訪客先抓到結論，再決定是否閱讀長文。

構圖以分支、節點、連線和留白建立層次。分類頁可以使用一條從問題到解法的水平路線，商品頁可以使用「主圖 → 規格 → 套裝 → 應用」的垂直路線。文字只作為必要標籤與行動指示，不能用長段落填滿畫面。每個圖示、分隔線、對齊點都要有理由，讓作品看起來像經過長時間校準的資訊圖，而不是套版卡片。

最後的品質標準是精準而非喧鬧：字距、表格欄寬、焦點框、圖片裁切、按鈕文案都要由同一套規則控制。需要冒險的地方只有一個——以「訊號地圖」作為每個頁面的可辨識簽名；其餘部分維持克制、安靜與高可讀性。成品必須像由熟悉電信現場與資訊設計的團隊反覆打磨，具備專業工藝、細節一致性與可長期維護的秩序。

### 3.3 內容語氣

- 服務頁：用「你要完成什麼」描述，不先講內部資料表或設備型號。
- 商品頁：先講套裝能完成的事情，再補充規格與品牌。
- 價格：明確標示「起」「月租」「一次性工程估價」的差異，不用模糊的「超值」代替數字。
- CTA：使用動詞，例如「查看涵蓋」「比較方案」「加入估價」「預約現勘」「送出需求」。
- 空資料：說明目前沒有可展示商品，並提供「聯絡我們詢問」或「返回服務分類」，不顯示空白頁。

### 4.2 商品分類頁

- 首屏只做三件事：顯示分類命題、提供搜尋／篩選、顯示主要商品群。
- 篩選維持 URL 狀態，例如 `?category=network&brand=tp-link`，讓結果可以分享與返回。
- 商品卡固定顯示：用途、品牌／系列、兩個最重要規格、供應狀態、加入估價。
- 不把 20 個規格全部放在卡片；其餘規格進商品詳情或可展開區。

### 4.3 商品詳情頁

1. 麵包屑與商品分類。
2. 主圖、商品名稱、短句用途、供應／保固狀態。
3. 三至五個關鍵規格，以資料標籤呈現。
4. 「這個組合適合誰」與「可以解決什麼問題」。
5. 包裝內容／建議搭配／安裝或維護服務。
6. 完整規格表、下載或詢價 CTA。
7. 相關商品、相關服務與回到首頁的路徑。

### 4.4 PHP 使用界線

| 使用情境 | 建議 |
|---|---|
| 固定服務介紹、固定商品文案 | `.html`，可快取、可直接分享 |
| 依資料庫即時顯示庫存、價格、促銷 | 現有 Node API + HTML/ES Module；若 VM 已是 PHP，再用 `.php` server-side render |
| 個人化報價、登入後價格、權限資料 | `.php` 或既有 API，但必須經伺服器驗證 |
| 檔案上傳、詢價寫入、訂單建立 | 不用純靜態 HTML；使用既有受保護 API |

不要為了「每頁一個檔案」複製整份 CSS、導覽與表單。共用頁首、頁尾、設計 token 和 CTA 契約要只有一份來源；檔案的獨立性只應存在於內容與路由，不應造成 UI 分叉。

### 5.2 導覽與 CTA

- 首頁導覽固定保留：網路方案、服務優勢、最新優惠、常見問題、立即申裝。
- 服務／商品內頁加上麵包屑與「回到服務分類」，不要求使用者依賴瀏覽器上一頁。
- 首頁方案 CTA 必須仍然導向 `#apply`；跨頁 CTA 使用 `/?intent=quote&product={slug}#apply` 或對應的固定詢價頁。
- 同一個行動在整個站點使用同一文案；例如「加入估價」不在下一頁突然變成「送出」。
- 任何外部品牌連結或 PDF 下載都要明示外開／下載，不在背景偷偷開分頁。

### 5.3 響應式與鍵盤

手機專用視覺尚未展開，但所有頁面仍需先避免基礎破版：

- 320px：單欄、CTA 全寬、表格可水平捲動，不讓整頁橫向溢出。
- 768px：服務卡兩欄，規格區改為可折疊或兩欄資料列。
- 1024px：桌面版主要驗收寬度；側邊分類與主內容並列。
- 1440px：內容最大寬度約 1200px，避免文字行過長。
- 所有按鈕使用原生 `<button>` 或 `<a>`；圖示按鈕有 accessible name。
- Dialog 開啟時移入焦點、`Esc` 關閉、關閉後還原原按鈕焦點。
- `prefers-reduced-motion` 關閉非必要的浮動、平滑捲動與自動輪播。

## 6. 首頁互動契約

以下是服務／商品頁接入首頁時不得破壞的既有契約：

| 互動 | 預期行為 | 驗證方式 |
|---|---|---|
| 導覽「網路方案」 | 導向 `#plans`，不重新載入頁面 | 檢查 hash、焦點與方案區可見 |
| 方案「查看完整詳情」 | 開啟原生 Dialog，載入單一方案資料 | 檢查 Dialog 標題、價格、`Esc` 與焦點返回 |
| Dialog「選擇此方案並申裝」 | 關閉 Dialog、導向 `#apply`、帶入選定方案並聚焦下拉選單 | 檢查 URL、select value、activeElement |
| 方案「選擇這個方案」 | 直接導向 `#apply` 並保留選定方案 | 檢查表單選項與 live region |
| 空白申裝表單送出 | 不送出網路請求，顯示欄位錯誤摘要並聚焦摘要 | 檢查姓名、聯絡方式、地址、同意欄位 |
| 首頁 → 服務內頁 | 內頁提供回首頁與回到同一服務分類的明確連結 | 檢查深連結與返回路徑 |
| 商品 → 詢價 | 保留商品 slug／服務意圖，不能只跳到沒有上下文的空表單 | 檢查 URL query、摘要文案與表單預選值 |
| API 載入失敗 | 顯示可重試、可理解的錯誤狀態 | 模擬 4xx／5xx，檢查 `aria-live` |
